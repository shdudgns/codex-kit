# Codex 프롬프트 예시

Codex 하나로 구현과 프롬프트 설계를 함께 하는 환경을 전제로 한다.

## 원칙

- 담당자에게 물을 질문 초안은 내가 먼저 쓴다(`interview.md`). 처음부터 "무엇을 물어야 하나"를 Codex에 맡기지 않는다.
- Codex는 데이터를 직접 확인해 근거 있는 질문을 뽑고, 내 초안에서 빠진 질문을 채우는 데 쓴다.
- 담당자 답을 매번 Codex에 옮기지 않는다. 들은 내용은 `docs/AGREEMENT.md`에 적고, Codex는 그 파일을 읽게 한다.
- 채택·수정·거절한 Codex 제안은 `docs/DECISIONS.md`에 이유와 함께 한 줄 남긴다.
- "README대로 다 구현해 줘"는 쓰지 않는다. 범위와 '이번에 하지 않을 것'을 함께 준다.

## A. 데이터 확인 → 담당자에게 물을 질문

```text
docs/skills/data-check/SKILL.md 절차대로 data/ 아래 데이터 파일을 확인해 줘. 파일 간 대조까지 해.
파일은 만들거나 고치지 말고, 결과를 표로만 보여 줘.
마지막에 "담당자에게 확인할 데이터 질문" 3~5개를 근거 수치와 함께 적어 줘. 해법은 제안하지 마.
```

## B. 내 질문 초안의 빈 곳 찾기

```text
담당자에게 보낼 질문 초안이야: (내 질문)
지금까지 들은 것: (요약 2~3줄)
누가·언제·무엇을 결정하는지, 반드시 지킬 규칙, 편의·효율 우선순위, 데이터 예외 기준으로 빠진 질문만 2~3개 추가해 줘. 해법은 제안하지 마.
```

## C. 합의문 모호점 점검

```text
docs/AGREEMENT.md와 docs/REQUIREMENTS.md를 읽고, 이대로 구현하면 네가 임의로 정하게 되는 부분(정의, 경계값, 예외, 출력 형태)을 목록으로만 보여 줘.
```

## D. 계획 요청

```text
docs/AGREEMENT.md 성공 기준과 docs/REQUIREMENTS.md를 만족하는 구현 계획을 모듈 단위로 보여 줘.
모듈마다 바꿀 파일, 실행 명령, 확인 방법, 대응하는 요구 ID를 적어. 아직 구현하지 말고 승인을 기다려.
```

## E. 요구사항 추적표 초안

```text
과제 README를 읽고 docs/REQUIREMENTS.md 표를 채워 줘. 요구 하나에 한 줄, 원문 표현을 줄이기만 하고 해석을 더하지 마.
금지 사항과 범위 밖은 원문 그대로 따로 적어. 상태 칸은 비워 둬.
```
(초안을 받으면 내가 README 원문과 한 줄씩 대조한다.)

## F. 최소 동작판 계획

```text
가장 단순한 방법으로 '규칙을 모두 지키는 결과를 과제가 정한 형식으로 내보내기'까지만 가는 계획을 보여 줘.
화면, 개선, 부가 기능은 빼. 검증기(G)를 같은 단계에 넣어. 승인을 기다려.
```

## G. 독립 검증기

```text
과제가 정한 출력 파일과 원본 입력만 읽고, 규칙마다 위반 목록을 내는 검증기를 만들어 줘.
생성 코드를 import하지 마. 규칙은 docs/AGREEMENT.md '반드시 지킬 규칙'에서 가져와.
일부러 위반을 넣은 작은 입력으로 검증기가 잡는지부터 테스트해.
```

## H. 변경·오류 입력 묶음

```text
원본 데이터를 바꾸지 않고, 생성 코드로 (1) 정상 변경본 (2) 오류 포함본을 새 폴더에 만들 계획을 보여 줘.
오류본에는 필수 열 누락, 없는 ID 참조, 형식 오류를 하나씩 넣어. 오류 메시지는 코드가 실제 검사로 만들게 해.
```
