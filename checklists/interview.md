# 담당자 인터뷰 (약 20분)

- 한 번에 2~3개씩, 짧고 구체적으로 묻는다. 데이터에서 뽑은 건수를 들고 묻는다.
- 담당자는 구현 방법·기능 목록·정답을 주지 않는 경우가 많다. "어떻게 만들까요" 대신 사실·우선순위·예외를 묻는다.
- 받은 답은 시각과 함께 docs/AGREEMENT.md에 옮긴다(확정). 답을 못 들은 항목은 가정으로 적고 설정값으로 노출한다.
- 질문 초안은 내가 먼저 쓰고, Codex는 데이터 근거 찾기와 빠진 질문 보완에만 쓴다(`codex-prompts.md`).

## 1. 목적과 성공 기준 (먼저)

- 이 결과를 누가, 언제, 어떤 결정에 쓰나요?
- 잘 됐다는 건 무엇으로 판단하나요? (지표, 기준값, 비교 대상)
- 지금은 이 일을 어떻게 하고 있고, 무엇이 가장 불편한가요?
- 꼭 필요한 것과 있으면 좋은 것을 나눠 주실 수 있나요?

## 2. 데이터

- 행 하나가 무엇을 뜻하나요? 각 컬럼의 의미와 단위, 키는요?
- 기간과 주기는요? 결측이나 이상값이 생기는 이유는요? 빼도 되나요?
- 같은 정보가 두 파일에서 다를 때 어느 쪽이 맞나요? (건수를 보여 주며)
- 상태·코드 값 중 뜻이 애매한 것(예: 목록에 없는 값)은 무엇을 뜻하나요?
- 정답(라벨)은 누가, 언제 정하나요? 예측 시점에는 알 수 없는 컬럼이 있나요?

## 3. 운영 규칙·최적화 과제일 때

- README 규칙 말고 현장에서 꼭 지키는 조건이 있나요? (반드시 vs 되도록)
- 이용자 편의의 상한은 어느 정도인가요? (기다림, 이동, 소요 시간 등)
- 효율과 편의가 부딪히면 무엇을 먼저 보나요?
- 규칙을 다 지킬 수 없는 대상(예외)은 어떻게 처리하나요?
- 날짜·시간 예외가 있나요? (자정을 넘는 시간, 휴일, 기본값과 다른 개인 일정)
- 결과가 날마다 바뀌어도 되나요, 같은 사람에게는 일정해야 하나요?
- 화면 문구 중 기준이 모호한 것(예: '거리', '다음', '현재')은 무엇을 기준으로 보나요?

## 4. 제약과 산출물

- 결과를 어떤 형태로 받고 싶으세요? (보고서, 화면, API, 파일)
- 놓치는 것과 잘못 잡는 것 중 무엇이 더 비싼가요?
- 해석 가능성, 속도, 실행 환경 같은 제약이 있나요?
- 이번 범위에서 빼도 되는 것은요?

## 5. 마무리

- "정리하면 … 이렇게 이해했는데 맞나요?" 요약을 보내 확인받고, 확인 시각을 합의문 제목에 적는다.
