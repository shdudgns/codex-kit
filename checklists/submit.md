# 제출 전 점검

## 웹 서비스 과제 (과제가 요구한 것만)

- [ ] 빈 DB(또는 새 볼륨)에서 시작해 스키마·초기 데이터가 준비된다
- [ ] 컨테이너 빌드가 처음부터 성공한다 (`docker build`)
- [ ] 재시작 후에도 데이터와 결과가 남아 있다
- [ ] 헬스체크 경로가 정상 응답한다
- [ ] 설정·비밀값이 환경변수로 들어가고 `.env.example`이 있다. 코드에 비밀값 없음 (`git grep -n -i "password\|secret"`로 확인)
- [ ] 역할별 계정으로 각각 로그인해 할 수 있는 일이 다르다
- [ ] 오류 입력 묶음을 적용하면 무엇이 틀렸는지 보이고, 기존 데이터·결과가 유지된다
- [ ] 새 입력을 적용한 뒤 재계산 전의 결과를 새 결과처럼 보여 주지 않는다
- [ ] 내보낸 결과를 독립 검증기로 돌려 위반 0 (입력 묶음별로)
- [ ] 과제가 보존하라고 한 파일이 그대로다 (`git diff --stat 첫커밋해시 -- README.md`)
- [ ] 과제가 정한 제출 문서가 양식 제목 그대로 있고 빈 칸이 없다 (해당 없으면 "해당 없음")

## 공통

- [ ] 과제 README가 요구한 파일명·경로가 맞다
- [ ] 실행 명령 한 줄로 처음부터 다시 돌려 봤다
- [ ] docs/REQUIREMENTS.md 상태 칸이 모두 채워졌다
- [ ] docs/HANDOFF.md에 핵심 숫자 5개, 30초 설명, 남은 한계, 외부 자료 출처가 있다
- [ ] git status가 깨끗하고 마지막 커밋이 있다
- [ ] 열린 파일이 모두 저장됐다
- [ ] 종료 10분 전에는 제출을 시작한다 (제출 후에는 고칠 수 없다고 가정)

## 마무리 직전: 확인 질문 대비

Codex에 한 번 요청한다.

```text
지금 저장소(코드, git log, docs/)를 보고 작성자가 결과물을 이해하는지 확인하는 질문 6개를 만들어 줘.
구현 범위, 확정 vs 가정, 알고리즘·설계 선택, 검증 방법, 예외·장애, 요구 변화 각 1개. 질문만 보여 줘.
```

그다음 REQUIREMENTS 상태 → DECISIONS 확정/가정 → HANDOFF 숫자 순서로 다시 읽는다.

### 답변 틀 (문항당 약 5분, AI 없이)

1. 결론: 무엇을 왜 그렇게 했는지 한 줄
2. 근거: 합의문 항목이나 데이터 수치
3. 약점: 내 코드·가정의 구체적 약점 하나
4. 파급: 그 약점이 터지면 무엇이 틀리는지
5. 다음 검증: 무엇을 확인하고 어떻게 고칠지

- 구현 범위 질문: 완료 n·부분 m·미구현 k → 미구현마다 이유 → 영향 → 다음 순서.
- 확정 vs 가정 질문: 확정(README·담당자 시각·데이터 수치) → 가정(못 들은 것 + 고른 이유) → 틀리면 영향 → 바꿀 위치.
- 질문의 전제가 실제 구현과 다르면 그 차이부터 밝힌다.
